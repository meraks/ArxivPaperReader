## Ch1：论文概述与核心贡献

### 1.1 一句话总结

Vortex 是一个面向 LLM 推理的**可编程稀疏注意力系统**，它通过 Python 嵌入式前端语言（vFlow）+ page-centric 张量抽象（vTensor）+ 高性能执行后端，让人类研究者和 AI Agent 都能在几分钟内完成稀疏注意力算法的原型设计、部署和评估，而不再需要数千行底层工程代码。

### 1.2 核心动机

LLM 推理中，注意力计算随生成长度呈二次增长。稀疏注意力是降低这一成本的关键技术——只对 KV cache 中的关键 token 做精确注意力计算。然而，当前生态存在三个严重的工程鸿沟：

| 鸿沟 | 问题 | 典型案例 |
|------|------|---------|
| **动态稀疏性难以泛化** | FlashInfer/FlexAttention 只加速"已知稀疏模式"的注意力，动态选块的代价可能超过注意力本身 | - |
| **缺乏可编程性** | 在 SGLang 中新增一个稀疏注意力变体需要约 2000 行代码 | Double Sparse → SGLang ≈ 2000 LOC |
| **与演进中的 serving 系统不兼容** | 自定义 kernel 与 paged attention、prefix caching 不兼容，理论加速在实测中消失 | Quest 原始实现比 SGLang full attention 慢 44.4× |

> **类比理解**：假设你要测试一种新的汽车发动机设计，但每次测试都需要：
> (a) 重新设计底盘、变速箱、悬挂系统（动态稀疏难泛化）
> (b) 每换一个设计理念就要重写整个控制软件（缺乏可编程性）
> (c) 测试结果与实际道路表现完全不符（与演进系统不兼容）
>
> Vortex 相当于提供了一个**标准化测试平台**：你只需要定义发动机的核心逻辑（vFlow ~50行），平台自动适配所有周边系统，且测试结果直接反映真实道路表现。

### 1.3 三项核心贡献

```
Vortex = vFlow（编程语言）+ vTensor（数据抽象）+ Execution Backend（执行引擎）
```

1. **vFlow**：Python 嵌入式的稀疏注意力编程语言。开发者（人或 AI Agent）只需实现 `forward_cache()` 和 `forward_indexer()` 两个方法，用"batch_size=1，逻辑连续 tensor"的心智模型编程。系统自动处理 batching、paging、caching。

2. **vTensor**：以 page 为中心的带布局元数据的 tensor 抽象。物理上 KV cache 是非连续的 paged 布局，vTensor 将其对上层透明化——开发者看到的永远是逻辑连续 tensor，vTensor 自动完成 layout propagation。

3. **Execution Backend**：编译器+运行时，将 vFlow 程序 lowering 到 vTensor 操作，构建 DAG，规划工作负载，融合 kernel，集成 FlashInfer/TensorRT-LLM/CUDA Graph/Radix Attention 等优化。

### 1.4 关键数字速览

| 场景 | 指标 | 数据 |
|------|------|------|
| AI Agent 自主发现 | Qwen3-1.7B, AIME, H200 | **3.46×** 吞吐量提升（vs full attention） |
| MLA 架构扩展 | GLM-4.7-Flash, B200 | **4.7×** 吞吐量提升 |
| 超大模型扩展 | MiniMax-M2.7 (229B), B200 | **1.37×** 吞吐量提升 |
| 编程效率 | Block Top-k 注意力 | **~50行** vFlow 代码 vs ~2000行 SGLang 实现 |
| 兼容性改善 | Quest 算法 | 从 44.4× 慢于 full attention → 实际加速 |

## Ch2：研究背景与动机

### 2.1 稀疏注意力的核心矛盾

在大规模 LLM 推理中，注意力计算的开销可以用以下公式刻画：

$$O_{\text{attn}} = O(T \cdot S)$$

其中 $T$ 为生成长度，$S$ 为已生成的序列长度。当生成数千个 token 时（如推理链、Agent 多步交互），$S$ 可能达到数万甚至数十万，注意力计算成为推理的主要瓶颈。

稀疏注意力的核心思想是：**在 $S$ 个 KV cache page 中，只选取 top-k 个与当前 query 最相关的 page 做精确注意力计算**：

$$o = \text{softmax}\left(\frac{qK_{\mathcal{I}}^T}{\sqrt{d}}\right) V_{\mathcal{I}}, \quad |\mathcal{I}| = k \ll S$$

> **类比理解**：想象你在图书馆找一本书。Full attention 相当于你把书架上每一本书都拿下来翻一遍。稀疏注意力相当于你只看目录卡片（block centroids），快速判断哪些书架区域最可能包含目标书，然后只去那几个区域找。关键在于：目录卡片必须轻量且准确，否则"找目录"的成本可能超过"直接翻书架"。

### 2.2 三大工程鸿沟详解

#### 鸿沟 1：动态稀疏性难以泛化

现有高效注意力算子（FlashInfer、FlexAttention）的优化基于一个前提：**稀疏模式在执行前已知**。但在很多场景中，稀疏模式是动态计算出来的：

```
# 动态稀疏注意力的一般流程
Step 1: 基于 query 和 KV cache 计算相关性分数（on-the-fly）
Step 2: 根据分数选取 top-k token/page
Step 3: 对选中的子集执行精确注意力
```

Step 1 的代价如果控制不好，可能超过 Step 3 节省的时间。现有框架对 Step 1 缺乏系统级支持。

#### 鸿沟 2：缺乏可编程性

以 SGLang 为例，实现一个新稀疏注意力算法需要：

```
1. 在 paged tensor 上重新实现 GeMM      (~300 LOC)
2. 在 paged tensor 上重新实现 Reduce     (~200 LOC)
3. 在 paged tensor 上重新实现 Top-K      (~250 LOC)
4. 集成到 attention backend              (~300 LOC)
5. 处理边界条件、batching、错误恢复      (~950 LOC)
─────────────────────────────────────────────────
总计                                    (~2000 LOC)
```

而且这些代码与特定的 serving 系统深度耦合，无法迁移。

#### 鸿沟 3：与演进中的 serving 系统不兼容

许多稀疏注意力方法的原始实现使用自定义 CUDA kernel，这些 kernel 通常：

- 假设 KV cache 是**连续内存布局** → 与 paged attention 的物理非连续布局冲突
- 不兼容 prefix caching → 长 prompt 场景无法复用已计算的 KV cache
- 不与 FlashInfer/TensorRT-LLM 等高效 attention backend 集成

结果是：论文报告的理论加速在端到端部署中完全消失。论文中 Quest 的案例——原始优化实现比 SGLang full attention 慢 44.4×——是对这一鸿沟最尖锐的说明。

### 2.3 Vortex 的解决思路

Vortex 将"**What**（什么稀疏模式）"与"**How**（如何高效执行）"分离：

```
What:  用户用 vFlow 表达稀疏模式选择逻辑（~50行 Python）
How:   Vortex 编译器+运行时处理 paging/batching/caching/kernel融合
```

这类似于数据库领域中 SQL（声明式 What）与查询优化器（自动决定 How）的关系。用户只需要描述"我想选哪些 page 做注意力"，Vortex 自动生成高效的执行计划。

## Ch3：vFlow —— Python 嵌入式编程模型

### 3.1 设计哲学

vFlow 的核心设计原则是**单请求心智模型**（single-request mental model）：

- 开发者假设 batch_size = 1（处理单个请求）
- 所有 tensor 看起来是逻辑连续的
- 无需关心 paging、batching、caching 等物理布局细节

系统在运行时透明地处理 batch expansion 和 layout translation。

### 3.2 两阶段编程接口

每个稀疏注意力算法由三个方法构成：

```python
class MySparseAttention(vFlow):
    def create_cache(self, block_size, head_dim):
        """声明 per-page 缓存结构（查询无关）"""
        return {"centroids": (1, head_dim)}

    def forward_cache(self, cache, k, v, page_indices):
        """查询无关预处理：更新 per-page 缓存"""
        # 例如：为每个新 page 计算 key 的均值作为 centroid
        ...

    def forward_indexer(self, q, cache, page_indices, num_available_pages):
        """查询相关执行：计算相关性分数并选择 top-k pages"""
        # 1. 计算 query 与每个 page centroid 的相似度
        # 2. 选取 top-k pages
        # 3. 返回选中的 page indices
        ...
```

**关键洞察**：
- `forward_cache()` 在 KV cache 更新时调用一次（低频，与新 token 数成正比）
- `forward_indexer()` 在每个 decode step 调用一次（高频，与生成长度成正比）
- 两者的分离使得**查询无关计算可以复用**，大幅降低 indexer 的负担

> **类比理解**：这就像搜索引擎的**索引构建**（forward_cache）和**查询检索**（forward_indexer）。Google 不会在每次搜索时扫描整个互联网——它预先构建了倒排索引。同样，Vortex 在 KV cache 更新时预计算 page 摘要（centroids），查询时只需要做轻量级的相似度匹配。

### 3.3 Block Top-k Attention 的 vFlow 实现

论文的核心运行示例：

**数学公式**：
$$\tilde{k}_j = \text{mean}(K[jb:(j+1)b-1]) \quad \text{(1: 计算 page centroids)}$$
$$\tilde{s}_j = \text{mean}(q\tilde{k}_j^T) \quad \text{(2: 计算 relevance scores)}$$
$$\mathcal{I} = \text{arg top-}k_{j} \tilde{s}_j \quad \text{(3: 选 top-k pages)}$$
$$o = \text{softmax}\left(\frac{qK_{\mathcal{I}}^T}{\sqrt{d}}\right) V_{\mathcal{I}} \quad \text{(4: 精确注意力)}$$

**vFlow 代码**（约20行核心逻辑）：

```python
from vortex_torch.flow import vFlow, register
from vortex_torch.indexer import topK, GeMM, Mean

@register("block_topk")
class BlockTopK(vFlow):
    def __init__(self):
        self.mean = Mean(dim=1)
        self.gemm = GeMM()
        self.output_func = topK()

    def forward_cache(self, cache, loc, ctx):
        # 公式(1)：预计算 page centroid
        self.reduction(cache["k"], cache["centroids"], loc=loc, ctx=ctx)

    def forward_indexer(self, q, o, cache, ctx):
        # 公式(2)：计算 q 与所有 centroids 的相似度
        q_mean = self.mean(q, ctx=ctx)
        score = self.gemm(q_mean, cache["centroids"], ctx=ctx)
        # 公式(3)+(4)：选 top-k 并输出
        self.output_func(score, o, ctx=ctx)

    def create_cache(self, block_size, head_dim):
        return {"centroids": (1, head_dim)}
```

开发者视角：所有 tensor 是逻辑连续的 `[1, B, d]` 形状。**不到 50 行代码**完成了从算法定义到部署就绪的全过程——而在 SGLang 中需要约 2000 行。

### 3.4 vFlow 的表达能力

vFlow 通过组合少量基础算子，可以覆盖多种主流稀疏注意力算法：

| 算法 | 核心思想 | vFlow 实现要点 |
|------|---------|---------------|
| **Block Top-k** | 按 page 聚合后选 top-k | `Mean(k)` → `GeMM(q_mean, centroids)` → `topK` |
| **Double Sparse** | 两级稀疏选择 | 先选 top-k tokens → 再在 token 级别精确计算 |
| **NSA (Block top-k 部分)** | DeepSeek 原生稀疏注意力 | Block-level 评分 + token-level 精确 |
| **Quest** | Query-aware 稀疏选择 | 动态计算 page 重要性，支持 GQA 近似 |
| **H2O** | Heavy Hitter Oracle | 累积 attention score 缓存 + 静态 top-k |

此外，vFlow 还支持：
- **静态稀疏模式**：从 sequence position 构造 index set（如 sliding window）
- **命名缓存**：`c["accumulated_scores"]` 跨 decode step 持久化
- **注意力后端切换**：`attn()` 调用透明路由到 FlashInfer 或 TensorRT-LLM

## Ch4：vTensor —— 以 Page 为中心的张量抽象

### 4.1 为什么需要 vTensor？

现代 LLM serving 系统使用 **paged attention**（源自 vLLM）管理 KV cache，物理内存布局如下：

```
物理内存（paged layout）：
  Page 0: |tok_0|tok_1|...|tok_15|     ← 可能物理上分散在 GPU 内存各处
  Page 1: |tok_16|tok_17|...|tok_31|
  Page 3: |tok_32|tok_33|...|tok_47|   ← Page 2 被另一个请求占用！
  ...
```

而 PyTorch tensor 假设**连续内存布局**。直接在 paged tensor 上编程意味着：
- 每个操作都需要处理间接寻址（通过 page table）
- 不同请求的 page 交错，无法使用标准 batching
- 代码充斥着 `gather`/`scatter` 和边界检查

### 4.2 vTensor 的形式化定义

vTensor 在 PyTorch tensor 上附加布局元数据：

$$x^v = (x, \mathcal{C}), \quad \mathcal{C} = (b, \mathbf{p}, \mathbf{I})$$

- $b$：batch size（逻辑上的序列数）
- $\mathbf{p}$：index pointer array（ragged layout 的起止位置）
- $\mathbf{I}$：page index structure（paged layout 的 page table）

三种布局类型：

| 布局 | 物理形态 | 使用场景 |
|------|---------|---------|
| **Contiguous** | 标准 PyTorch tensor | 输入 query，中间计算结果 |
| **Ragged** | 变长序列拼接，通过 pointer 分隔 | batch 中不同长度的序列 |
| **Paged** | 通过 page table 间接寻址的非连续块 | KV cache |

### 4.3 Operator 语义

对于任意算子 $F$，vTensor 的执行语义是**独立应用于 batch 中的每个序列**，然后聚合结果：

```python
# 伪代码：vTensor 的算子执行
for i in range(batch_size):
    # 1. 从 vTensor 中提取第 i 个序列的数据
    seq_data = extract_sequence(vtensor, i)
    # 2. 应用标准 PyTorch 算子
    result_i = F(seq_data)
    # 3. 聚合到输出 vTensor
    aggregate(output, result_i, i)
```

**关键约束**：vTensor **禁止跨序列操作**。这一方面匹配 LLM serving 的实际需求（每个请求独立），另一方面大幅简化了实现——不需要处理跨序列的内存合并。

### 4.4 vFlow → vTensor 的 Lowering

编译器将 vFlow 变量映射到 vTensor：

```
vFlow 变量           →  vTensor
─────────────────────────────────────────
q (query)            →  Contiguous vTensor (batch × d)
c["centroids"]       →  Paged vTensor (per-page cache)
s (scores)           →  Ragged vTensor (per-sequence scores)
i (selected indices) →  Ragged vTensor (per-sequence indices)
```

**命名缓存**（如 `c["centroids"]`）被存储为 paged vTensor，与 KV cache 共享相同的 paging/分配机制，天然兼容 prefix caching。

> **类比理解**：vTensor 相当于操作系统的**虚拟内存**。程序看到的是连续的虚拟地址空间（vFlow 中的逻辑连续 tensor），而 vTensor 像 MMU（内存管理单元）一样透明地完成虚拟地址到物理 page 的映射。开发者不需要知道数据在物理内存中的位置，就像你不需要知道 malloc 返回的内存实际在哪个 DRAM bank 上。

## Ch5：执行后端优化

### 5.1 整体架构

```
vFlow 源码 (.py)
      │
      ▼
  编译器 ──→ DAG 构建（operator dependency graph）
      │
      ▼
  工作负载规划器 ──→ 将 DAG 切分为 chunks
      │
      ▼
  Kernel 生成器 ──→ JIT 编译 Triton/CUDA kernel
      │
      ▼
  运行时调度 ──→ 集成 CUDA Graph / Radix Attention
```

### 5.2 Chunk-based 执行模板

对于批量 operator（GeMM、elementwise、reductions），Vortex 使用通用 chunk-based 模板：

```
for each chunk of pages:
    1. 加载 chunk 中的 page 数据到 shared memory / registers
    2. 执行 operator（使用 JIT 编译的 kernel）
    3. 将结果写回 vTensor
```

chunk 大小由 workload planner 根据 operator 类型和 GPU 特性（SM 数量、shared memory 大小）自动选择。

### 5.3 Kernel Fusion

相邻 operator 被 fused 为单个 kernel 以减少内存往返：

```python
# Before fusion:
t1 = GeMM(q, centroids)    # read centroids → write t1
t2 = Softmax(t1)           # read t1 → write t2
t3 = TopK(t2)              # read t2 → write t3

# After fusion (single kernel):
t3 = Fused_Score_Select(q, centroids)
# 所有中间结果在 register / shared memory 中传递
```

### 5.4 与 Serving Stack 的深度集成

Vortex 的执行后端与 SGLang 的 serving stack 紧密集成：

- **FlashInfer**：默认的稀疏注意力后端，处理选中 pages 的精确 softmax attention
- **CUDA Graph**：将 indexer + attention 的计算图捕获为 CUDA Graph，消除 kernel launch overhead
- **Radix Attention**：兼容 prefix caching，共享的 prefix 的 page centroids 可复用
- **Custom MLA kernel**：针对 MLA（Multi-head Latent Attention）架构（如 GLM-4.7-Flash）的定制 kernel

### 5.5 VortexConfig：声明式配置

所有稀疏注意力参数集中在一个 dataclass 中：

```python
@dataclass
class VortexConfig:
    module_path: str        # vFlow 定义文件路径
    module_name: str        # 注册的 vFlow 名称
    topk_val: int = 30      # 静态 page budget（最少保留的 page 数）
    topk_ratio: float = 0.0 # 动态 page budget（比例）
    block_size: int = 16    # Vortex page 大小（稀疏度单位）
    layers_skip: list = None # 跳过稀疏的 layer（如前几层用 dense）
    attention_backend: str = "flashinfer"  # 注意力后端
    schedule_policy: str = None  # CUDA C++ 自定义调度策略
    ...
```

这使 Vortex 与 SGLang 的集成极其简单：

```python
import sglang as sgl
import vortex_torch

engine = sgl.Engine(
    model="Qwen/Qwen2.5-1.5B-Instruct",
    vortex_config=vortex_torch.VortexConfig(
        module_name="block_topk",
        topk_val=30,
        block_size=16,
    )
)
response = engine.generate("What is the capital of France?")
```

## Ch6：AI Agent 自主算法发现

### 6.1 设计动机

Vortex 最独特的贡献在于：它将稀疏注意力算法的设计从一个**人类工程师的专属领域**转变为**AI Agent 可以自主完成的工作**。

传统工作流：人类研究者 → 设计算法 → 手动实现（~2000 LOC）→ 集成测试 → 调整 → 循环。每次迭代可能需要数天。

Vortex 工作流：AI Agent → 生成 vFlow 代码（~50 LOC）→ 自动部署到 SGLang → 自动 benchmark → 基于结果迭代。每次迭代只需几分钟。

### 6.2 Agent 工作空间

仓库的 `AI/` 目录包含 Claude Code 和 OpenHands 的预制 workspace：

```
AI/
  claude_code/     - Claude Code 的 agent 配置和 prompt
  openhands/       - OpenHands 的 agent 配置
```

`submissions/` 目录展示了各 AI Agent 的产出：

```
submissions/
  claude_opus_4_7/    - Anthropic Claude Opus 4.7 生成的算法
  claude_sonnet_4_6/  - Anthropic Claude Sonnet 4.6 生成的算法
  gpt_5/              - OpenAI GPT-5 生成的算法
  kimi_v0.py          - Moonshot Kimi 生成的算法
  oai_v0.py           - OpenAI 生成的算法（另一个版本）
```

每个 submission 包含：
- `.py` 文件：vFlow 算法定义（通常 50-150 行）
- `.json` 文件：配置参数（`VortexConfig`）

### 6.3 Algorithm Scientist 迭代框架

`algorithm_scientist/` 目录提供闭环迭代框架：

```
1. Agent 生成 vFlow 代码
2. Vortex 自动部署到 SGLang
3. 在 benchmark 上评估（吞吐量 + 准确率）
4. 结果反馈给 Agent
5. Agent 分析瓶颈并提出改进
6. 重复 1-5
```

### 6.4 关键结果

AI Agent 在 Qwen3-1.7B + AIME benchmark 上发现的最佳算法：

- **3.46×** 吞吐量提升 vs full attention
- **准确率保持**（AIME 任务得分无明显下降）
- 这说明 Agent 不仅找到了高效的稀疏模式，而且选择的 token/page 确实包含了任务所需的关键信息

> **类比理解**：这就像 AlphaGo 下围棋——人类提供了游戏规则（vFlow API），而 AI 在规则空间内探索出了人类可能未曾想到的"定式"。某些由 Agent 发现的稀疏模式可能与人类直觉完全不同，但在实际推理中更高效。

### 6.5 "Routing Signal 在哪里？"

论文指出 Vortex 还可以作为**研究工具**帮助理解稀疏注意力的内在机制：

- 不同 Agent 发现的算法选择 page 的标准各不相同
- 有的基于 query-key 相似度，有的基于 attention score 的历史累积
- 通过对比不同算法的行为，可以研究"稀疏注意力中的 routing signal 究竟在哪里"

## Ch7：实验结果与分析

### 7.1 实验设置

| 维度 | 设置 |
|------|------|
| 模型 | Qwen3-1.7B, Qwen3-14B, GLM-4.7-Flash, MiniMax-M2.7 (229B) |
| GPU | NVIDIA H200, B200 |
| Benchmark | AIME（推理密集型长生成任务） |
| Serving 框架 | SGLang + Vortex 集成 |
| Baseline | Full attention（SGLang 原生） |

### 7.2 吞吐量提升

**小型模型（Qwen3-1.7B, H200）**：
- AI Agent 发现的最佳算法：**3.46×** 吞吐量提升
- 多种 Agent 生成的算法均超过 2×

**MLA 架构（GLM-4.7-Flash, B200）**：
- **4.7×** 吞吐量提升
- MLA（Multi-head Latent Attention）的 KV cache 较小，但 Vortex 仍能显著提升——说明优化不限于标准 MHA 架构

**超大规模模型（MiniMax-M2.7, 229B, B200）**：
- **1.37×** 吞吐量提升
- 229B 参数模型的 attention compute 已经是巨额开销，即便是 37% 的提升在实际部署中也意味着显著的成本节约

### 7.3 准确率保持

- 在 AIME benchmark 上，3.46× 加速的算法保持了与 full attention 相当的准确率
- 说明选中的 sparse page 确实覆盖了推理所需的关键上下文
- 论文中展示的 ablation 表明：过激的稀疏化（如 page budget 过低）会导致准确率下降

### 7.4 编程效率

| 实现方式 | 代码量 | 开发时间 |
|---------|--------|---------|
| SGLang 原生（Double Sparse） | ~2000 LOC | 数天 |
| Vortex vFlow（Block Top-k） | ~50 LOC | 数分钟 |
| Vortex vFlow（AI Agent 生成） | ~50-150 LOC | 数分钟（自动） |

### 7.5 系统开销分析

Vortex 的 indexer 本身有计算开销（计算 centroids、dot product 评分、top-k 选择）。论文的关键发现是：

- 在长生成场景中，indexer 开销**远小于**被节省的 attention 计算
- indexer 的 chunk-based 执行 + kernel fusion 使其开销仅占总耗时的很小比例
- 随着生成长度增加，稀疏注意力的收益持续扩大

### 8.5 示例：AI Agent 生成的算法骨架

```python
# Source: submissions/example_block_sparse_attention.py
from vortex_torch.flow import vFlow, register
from vortex_torch.indexer import topK, GeMV, Softmax, Max, Sum, GeMM, Maximum, Multiply, Add, L2Norm, Save, Load, Mean, MaskSlice
from vortex_torch.cache import Mean as CMean, Max as CMax, Min as CMin, L2Norm as CL2Norm
from vortex_torch.abs import ContextBase

@register("example_block_sparse_attention_cls")
class ExampleBlockSparseAttentionCls(vFlow):
    def __init__(self):
        super().__init__()
        self.gemm = GeMM()
        self.mean = Mean(dim=1)
        self.output_func = topK()
        self.reduction = CMean(dim=1)

    def forward_indexer(self, q, o, cache, ctx):
        q_mean = self.mean(q, ctx=ctx)
        score = self.gemm(q_mean, cache["centroids"], ctx=ctx)
        self.output_func(score, o, ctx=ctx)

    def forward_cache(self, cache, loc, ctx):
        self.reduction(cache["k"], cache["centroids"], loc=loc, ctx=ctx)

    def create_cache(self, block_size, head_dim):
        return {"centroids": (1, head_dim)}
```

## Ch9：局限性与延伸阅读

### 9.1 论文局限性

1. **GPU 限定**：Vortex 当前仅支持 NVIDIA GPU（H200/B200），未涉及 AMD、Intel 或 Apple Silicon 等平台。

2. **Attention-only 优化**：Vortex 仅优化注意力计算。在 short-context 场景或 compute-bound 模型（如 dense FFN 占主导）中，收益有限。

3. **SGLang 依赖**：当前后端仅集成 SGLang，虽然架构上可扩展到 vLLM 或其他 serving 框架，但尚未实现。

4. **Agent 生成算法的可解释性**：AI Agent 发现的算法虽然高效，但其选择 page 的策略可能难以解释。论文将 Vortex 定位为研究工具来探索"routing signal 在哪里"，但尚未给出系统性结论。

5. **Page size 敏感性**：稀疏度的基本单位是 Vortex page（默认 16 tokens），page size 的选择对效率有显著影响，但目前需要手动调优。

6. **动态 page budget**：`topk_ratio` 的动态分配策略较为朴素，论文提到可扩展为基于模型置信度的自适应策略。

### 9.2 与相关工作的关系

| 工作 | 关系 |
|------|------|
| **FlashInfer** | Vortex 的执行后端使用 FlashInfer 作为稀疏注意力 kernel |
| **FlexAttention (PyTorch)** | 类似的可编程注意力接口，但不支持 paged layout |
| **SGLang** | Vortex 深度集成到 SGLang 的 serving pipeline |
| **vLLM (PagedAttention)** | vTensor 的 paged layout 概念继承自 vLLM 的 PagedAttention |
| **DeepSeek NSA** | 论文中 NSA 的 block top-k 部分可用 vFlow 表达 |
| **Quest / H2O** | 可在 Vortex 中作为 vFlow 实现，从 44.4× 慢变为实际加速 |

### 9.3 影响力与展望

Vortex 最重要的贡献可能不是某个具体的加速数字，而是**范式转换**：

- **从手工工程到可编程抽象**：就像 PyTorch 取代了手写 CUDA kernel、SQL 取代了手写 B-tree，vFlow 可能成为稀疏注意力领域的"标准语言"。
- **从人类设计到 AI 探索**：AI Agent 自主发现算法的成功表明，稀疏注意力设计空间可能远大于人类直觉，Vortex 提供了系统化探索这一空间的平台。
- **从研究到部署的零摩擦**：vFlow 代码可直接部署到生产 serving 系统，消除了"论文发表→工程实现→实际部署"之间的漫长鸿沟。

## 附录：核心术语速查表

| 术语 | 含义 |
|------|------|
| **vFlow** | 稀疏注意力算法的 Python 嵌入式编程语言 |
| **vTensor** | 带布局元数据的张量抽象（支持 contiguous/ragged/paged） |
| **Paged Attention** | 将 KV cache 划分为固定大小的 page，通过 page table 间接寻址 |
| **Block Top-k** | 按 page 聚合 key 为 centroid → 选 top-k pages → 精确注意力 |
| **MLA** | Multi-head Latent Attention（DeepSeek/GLM 的压缩注意力架构） |
| **CUDA Graph** | 将 GPU 操作序列预编译为执行图，消除 kernel launch overhead |
| **Radix Attention** | 基于前缀树（radix tree）的 prefix caching 技术 |
| **Indexer** | vFlow 中查询相关的执行阶段（选 page） |
| **Cache** | vFlow 中查询无关的预计算阶段（更新 page 摘要） |
| **Routing Signal** | 稀疏注意力中选择哪些 token/page 的依据信号 |
