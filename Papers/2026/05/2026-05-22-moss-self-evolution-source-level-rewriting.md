## 一、研究背景与动机

### 1.1 问题：部署后的智能体是"静态"的

当前自主智能体（autonomous agent）系统在部署后存在一个根本性的问题：**它们是静态的**。一旦上线运行，系统无法从用户交互中学习，反复出现的错误会一直存在，直到人类开发者手动发布下一个更新版本。

这种"部署即固化"的模式导致：
- **用户体验持续恶化**：相同的错误反复出现，用户信心不断下降
- **运维成本高昂**：需要人工诊断问题、编写修复代码、测试、重新部署
- **迭代周期长**：从发现问题到修复上线可能需要数天甚至数周

### 1.2 现有方案的局限：只能在"文本层"打转

现有的自我进化智能体（如 Hermes Agent、SkillClaw、GenericAgent、EvoAgentX）虽然试图让智能体自我改进，但它们的进化范围被严格限制在**文本可编辑产物**（text-mutable artifacts）上：

| 系统 | Skill | Prompt | Memory | Harness |
|------|:-----:|:------:|:------:|:-------:|
| Hermes Agent (Nous Research, 2024) | ✅ | ❌ | ✅ | ❌ |
| SkillClaw (Ma et al., 2026) | ✅ | ❌ | ❌ | ❌ |
| GenericAgent (Liang et al., 2026) | ✅ | ❌ | ✅ | ❌ |
| EvoAgentX (Wang et al., 2025) | ✅ | ✅ | ❌ | ❌ |
| **MOSS (本文)** | **✅** | **✅** | **✅** | **✅** |

可以看到，现有系统都**无法触及智能体的 harness（框架层）**——包括消息路由、钩子排序、状态管理、调度逻辑等核心代码。而这些恰恰是大量生产环境错误的来源。

> 论文原文指出："failures originating in routing, hook ordering, state invariants, or dispatch are physically unreachable from the text layer."

### 1.3 为什么源码级自适应更好？（四个维度）

MOSS 提出，源码级自适应（source-level adaptation）在四个关键维度上全面优于文本层进化：

| 维度 | 说明 |
|------|------|
| **图灵完备** (Turing-complete) | 源代码的设计空间是通用的，所有文本可编辑空间都是其严格子集 |
| **严格超集** (Strict superset) | prompt 编辑能做到的，代码编辑也能做到；但反过来不行 |
| **确定性效果** (Deterministic effect) | 路由逻辑、钩子排序作为代码执行，不依赖基座模型对文本指令的服从度 |
| **无长上下文漂移** (No long-context drift) | 修改被编码为行为（代码），而非需要反复读取的文本；不会随系统老化而退化 |

## 二、核心贡献

本文的主要贡献可以总结为以下几点：

1. **提出源码级自我进化范式**：首次将智能体的自我进化范围从文本可编辑层扩展到 agent harness（框架层）的源码重写，实现了图灵完备的进化空间。

2. **设计了 MOSS 系统架构**：包含主容器、控制面 CLI、可插拔编码智能体、宿主机守护进程和临时试验工作器五个核心组件，形成完整的自动进化流水线。

3. **提出有向进化（Directed Evolution）机制**：区别于探索性进化，MOSS 的进化以生产环境中的实际失败证据为锚点，通过自动扫描和用户标记两个渠道收集证据。

4. **设计了七阶段确定性流水线**：从定位、规划、实现到验证，每一步都有质量门控（quality gate），确保进化的正确性和安全性。

5. **实现了安全的容器热替换机制**：通过 90 秒健康探针窗口、连续 3 次通过检验、自动回滚等机制，确保容器升级不影响用户服务。

## 三、方法详解

### 3.1 整体架构

MOSS 由五个核心组件构成：

```
┌─────────────────────────────────────────────┐
│              Host Machine                    │
│                                              │
│  ┌─────────────┐     ┌──────────────────┐   │
│  │ Host Daemon │─────│ Coding Agent CLI │   │
│  │ (asyncio)   │     │ (Claude Code/    │   │
│  │             │     │  Codex/DeepSeek/ │   │
│  │  ┌───────┐  │     │  OpenCode)       │   │
│  │  │moss   │  │     └──────────────────┘   │
│  │  │evo CLI│  │                             │
│  │  └───────┘  │     ┌──────────────────┐   │
│  └──────┬──────┘     │ Trial Workers    │   │
│         │            │ (ephemeral)      │   │
│  ┌──────▼──────┐     └──────────────────┘   │
│  │   Main      │                            │
│  │  Container  │ ←── User State Volume      │
│  │ (Agent +    │     (sessions, memory,     │
│  │  moss evo)  │      credentials, configs) │
│  └─────────────┘                            │
└─────────────────────────────────────────────┘
```

**组件 1：主容器 (Main Container)**
- 运行面向用户的 agent 系统
- 包含容器内进化服务
- 绑定挂载 `moss evo` CLI 工具

**组件 2：控制面 CLI (`moss evo`)**
- 提供 9 个子命令：`status`、`batches`、`batch`、`start`、`stop`、`restart`、`apply`、`flag`、`catch-up`
- 是用户与 MOSS 系统交互的主要接口

**组件 3：可插拔外部编码智能体**
- 每个阶段作为宿主机子进程调用
- 内置 4 种运行器：Claude Code、OpenAI Codex、DeepSeek-TUI、OpenCode
- 添加新编码智能体只需一个文件 + 一行注册代码

**组件 4：宿主机守护进程 (Host Daemon)**
- asyncio 进程，负责：编码智能体调用、试验工作器生命周期、Docker 构建、自动扫描引擎、容器替换监控

**组件 5：临时试验工作器 (Ephemeral Trial Workers)**
- 每次迭代创建 N 个短生命周期容器
- 用于运行时验证（而非单元测试）
- 网络和挂载隔离，防止影响在线系统

### 3.2 底层集成契约

任何智能体框架只需提供**五个原语**即可接入 MOSS：
1. **Shell 等效工具执行** — 能执行命令行操作
2. **文件系统读取** — 能读取配置和状态文件
3. **周期性调度** — 支持定时任务
4. **Webhook 到智能体传递** — 能接收外部通知
5. **系统提示注入** — 能向智能体注入指令

这意味着 MOSS 具有很强的通用性，可以适配多种不同的智能体框架。

### 3.3 有向进化过程

#### 3.3.1 证据收集（两条渠道）

MOSS 的进化是**有向的（directed）**而非探索性的——每一次进化都以实际的生产失败证据为驱动：

**渠道 1：自动扫描 (Auto-scan)**
- 通过定期 cron 任务 (`moss evo catch-up`) 执行
- 对会话 JSONL 数据块进行评分
- 弱/缺失的关键点追加到当前批处理中

**渠道 2：用户标记 (User Flagging)**
- 用户通过 `moss evo flag` 主动报告不满意
- 直接注入证据队列

#### 3.3.2 批处理管理

- 每个对话维护一个开放的批处理（batch）
- 在可配置阈值处封口（默认：8 个数据块/chunks）
- 封口后进入进化流程

#### 3.3.3 迭代循环

- **有界循环**：在批处理修复完毕或进一步工作无效时退出
- **进化深度拨盘**：`light`（轻量）、`standard`（标准）、`deep`（深度），控制迭代预算、轮次预算、试验数量、平台阈值
- **平台守卫**：当关键点连续多轮无改善时，强制收敛
- **四种判定结果**：
  - `CONVERGED` — 问题已修复
  - `NEED_MORE_WORK` — 需要继续迭代
  - `FUNDAMENTAL_LIMIT_MODEL` — 基座模型能力限制
  - `FUNDAMENTAL_LIMIT_ARCHITECTURE` — 架构层面限制

### 3.4 七阶段流水线

每次迭代经过严格的七阶段流水线：

| 阶段 | 功能 | 说明 |
|------|------|------|
| **1. Locate（定位）** | 读取基线追踪记录 | 只写诊断分析，不提出修复方案 |
| **2. Plan（规划）** | 识别根本原因 | 指定哪些文件需要修改 |
| **3. Plan-Review（规划审查）** | 质量门控 | 批准/拒绝（可能偏离目标/范围过窄），支持多轮规划循环 |
| **4. Implement（实现）** | 编写代码 | 作为单个 git commit 提交 |
| **5. Code-Review（代码审查）** | 质量门控 | 对照规划审查差异，支持多轮代码循环（轮次间硬重置） |
| **6. Task-Evaluate（任务评估）** | 评分 | 每个任务评估 4-7 个关键点，使用 4 级评分（strong/adequate/weak/missing） |
| **7. Verdict（判定）** | 综合决策 | 综合评估结果和跨迭代关键点矩阵，给出最终判定 |

**关键设计亮点**：
- **双重质量门控**：Plan-Review 和 Code-Review 两个阶段确保修改的质量
- **多轮迭代**：规划和代码阶段都支持多轮循环，直到通过审查
- **硬重置**：代码审查轮次间会硬重置，避免前一轮的残留影响
- **量化评估**：使用 4 级评分体系对每个关键点打分，提供客观的改进度量

### 3.5 运行时验证

MOSS 的验证机制非常独特：

- **不是单元测试**——而是使用临时试验工作器在**生产等效容器**中重放批处理任务
- **隔离环境**：试验工作器与在线容器网络和挂载隔离
- **多次试验**：每个任务执行多次试验以暴露不稳定性（flakiness）
- **生产等效**：在尽可能接近真实环境的情况下验证修复效果

### 3.6 容器热替换机制

这是 MOSS 最精彩的设计之一——安全地在线升级运行中的智能体容器：

1. **判定收敛** → 触发 webhook → 智能体通知用户
2. **用户同意** → 用户执行 `moss evo apply`（**用户授权门控**）
3. **容器替换** → 宿主机守护进程写入替换请求 → 用候选镜像重启容器
4. **90 秒健康探针窗口**（每 5 秒采样一次）：
   - 心跳 ≤ 30 秒
   - 容器正在运行
   - 2 个底层 CLI 探针通过
5. **连续 3 次通过** → 提交替换；否则 → **自动回滚到上一个已知良好镜像**

**用户状态保护**：
- 用户状态（会话、记忆、凭据、配置）存储在**宿主机挂载卷**上
- 容器替换时用户状态完全保留，不受影响

## 四、实验结果

### 4.1 实验设置

- **底层智能体框架**：OpenClaw
- **基座模型**：DeepSeek V3.2
- **任务集**：4 个 claweval 合规审计任务
- **评估方式**：合规性评分（compliance score），越高越好

### 4.2 主要结果

| 任务 | 描述 | 基线分数 | 迭代 1 后 | 提升幅度 |
|------|------|----------|-----------|----------|
| T141zh | SLA 审计（中文） | 0.3273 | 0.5330 | +62.8% |
| T142 | SLA 审计（英文） | 0.2527 | 0.5453 | +115.8% |
| T137zh | 补货审计（中文） | 0.2213 | 0.4567 | +106.4% |
| T138 | 补货审计（英文） | 0.2090 | **0.9049** | +332.9% |
| **平均** | — | **0.2526** | **0.6100** | **+141.5%** |

**一次迭代后平均分数从 0.25 提升到 0.61，涨幅高达 141.5%！**

### 4.3 修复分析

修复仅涉及 **3 个文件**，**177 行新增**，**1 行删除**：
- 新增了工具结果中介器（tool-result mediator）中的注解分支
- 新增了预调用拒绝门（pre-call deny gate），阻止批处理 shell 模式
- 新增了中介器测试文件

**核心洞察**：这个修复**修改的是 harness 本身**——路由逻辑和请求预处理——而不是任何文本可编辑产物。这恰恰是现有系统**无法触及的层面**。

## 五、关键发现与洞察

### 5.1 文本层进化的天花板

论文揭示了一个深刻的现实：当前所有"自我进化"智能体系统实际上都在一个受限的空间里操作。它们可以修改提示词、更新记忆、调整技能描述，但无法修复**框架层面的 bug**——而恰恰是这些框架层问题（路由错误、钩子顺序不当、状态不变量破坏）导致了大量生产环境故障。

### 5.2 代码即行为，文本即指令

一个关键的设计哲学区别：
- **文本层进化**：通过修改文本指令来**试图改变**模型行为——但模型是否遵守取决于其指令服从能力
- **源码层进化**：直接将修复编码为**确定性的代码行为**——不依赖模型的服从度

这意味着源码层修复更加可靠和可预测。

### 5.3 长上下文漂移问题

文本层进化面临一个被忽视的问题：随着系统进化次数增多，需要注入的文本指令越来越长，模型需要阅读的上下文也越来越多——这会导致注意力稀释和行为退化。源码层进化将修改编译为行为，不存在这个问题。

### 5.4 安全性设计的多层次保障

MOSS 的安全设计值得特别关注：
- **用户授权门控**：每次容器替换都需要用户明确同意
- **健康探针验证**：90 秒内连续 3 次通过
- **自动回滚**：验证失败自动恢复到上一版本
- **用户状态独立**：状态保存在外部卷，替换不影响数据
- **隔离验证**：试验工作器与在线系统完全隔离

### 5.5 实用主义的进化策略

MOSS 选择"有向进化"而非"探索性进化"是一个明智的工程决策：
- **有证据驱动**：只有出现了实际问题时才触发进化
- **有界迭代**：不会无限制地搜索最优解
- **有平台检测**：当无法继续改进时及时停止
- **有根本原因分类**：区分模型限制和架构限制，帮助人类开发者介入

## 六、个人评述

### 优势

1. **问题定义精准**：论文准确识别了现有自我进化智能体系统的核心局限——进化空间的边界。这是一个被社区广泛忽视但确实存在的问题。

2. **工程实现扎实**：五组件架构、七阶段流水线、容器热替换等设计体现了丰富的分布式系统工程经验。尤其是健康探针 + 自动回滚的设计，是成熟工程实践的表现。

3. **安全优先**：在 AI 自主修改自身代码这个敏感场景下，MOSS 设计了多层安全保障（用户授权、隔离验证、自动回滚），这是负责任的做法。

4. **通用性强**：五个原语的集成契约使得 MOSS 可以适配多种不同的智能体框架。

### 局限与思考

1. **实验规模有限**：仅在一个框架（OpenClaw）和 4 个任务上验证，且只展示了一次迭代的结果。缺乏更广泛、更长期的评估。

2. **成本问题**：每次迭代需要调用外部编码智能体（如 Claude Code），这可能产生显著的 API 调用成本。论文未讨论成本分析。

3. **安全性担忧**：虽然设计了多层保障，但让 AI 自主修改生产代码仍然是一个高风险操作。一个巧妙的"看起来正确但实际有害"的代码修改可能通过所有质量门控。

4. **编码智能体依赖**：MOSS 本质上将"修改代码"的能力委托给了外部编码智能体（如 Claude Code），系统的进化质量上限受限于这些编码智能体的能力。

5. **缺少对比实验**：没有与文本层进化方法（如仅修改 prompt/skill）的直接对比，无法量化"源码级进化"相对于"文本层进化"的具体优势幅度。

6. **可复现性**：代码仓库在论文发表时似乎不可访问，影响了结果的可复现性。

### 总体评价

MOSS 代表了智能体自我进化研究的一个重要方向——从文本层的"表面进化"走向源码层的"深层进化"。虽然实验验证还不够充分，但其系统设计和工程思路对整个社区有重要的参考价值。这个工作也引发了一个更深层的问题：当 AI 系统能够自主修改自身源码时，我们如何确保这种修改始终是安全和有益的？
