## 第 1 章 概述

### 1.1 一句话定位

LongStraw 是一个面向固定 GPU 预算的架构感知执行栈，通过分离共享提示词（prompt）与响应（response）的计算路径，将 GRPO 后训练的上下文长度扩展到百万 token 级别，在 8 块 H20 GPU 上完成 2.1M token 的分组评分与反向传播。

LongStraw 回答的核心问题是：**在 GPU 数量固定（不增加设备）的情况下，GRPO 训练能支持多长的上下文？** 这与现有工作（Ring Attention、DeepSpeed-Ulysses）通过增加 GPU 数量来扩展上下文的路线互补。

### 1.2 核心贡献

1. 提出共享提示词执行设计：提示词一次性无梯度计算并保存架构感知状态，响应分支逐个回放（replay）以限制活动计算图规模，将活动内存从 $P+R$ 降低到 $R$。
2. 在两个截然不同的模型族上实现该设计：Qwen3.6-27B（混合循环/全注意力 GDN + 密集 FFN）和 GLM-5.2（MLA/DSA 压缩注意力 + MoE），验证了设计的通用性。
3. 报告完整的执行路径、时序和内存测量，同时明确声明四个证据层次中哪些已完成、哪些未验证，提供了系统的开源训练系统参考。

### 1.3 关键结果速览

- **Qwen 2.1M context**：在 8 块 H20 GPU 上完成 G=2 和 G=8 的 GRPO 分组评分与反向传播；分组规模从 2 增加到 8 仅增加 0.21 GB 峰值内存（0.213%），体现串行回放的内存优势。
- **压力测试上限**：Qwen 在 8 块 H20 上达到 4,456,448 位置（4.25M）的 G=8 完整回放，峰值 82.960 GB/rank；train-block proxy 进一步推进到 4,538,368 位置。
- **GLM 端到端验证**：在 32 块 H20 GPU 上验证跨全部 78 层的 2.1M-token 执行路径；G=2 完成时间 2,975 秒；CPU 前缀存储 5.8125 GiB/rank（聚合 186 GiB）。
- **核心洞察**：状态生命周期（state lifetime）和物理所有权（physical ownership）是决定 RL 后训练实际上下文极限的关键因素，而非仅注意力稀疏性或模型参数大小。

### 1.4 与现有方法的对比

LongStraw 并非首个尝试长上下文训练的系统，但它的定位独特。与以下现有方案形成对比：

| 方案 | 方法 | 最大上下文 | 硬件配置 |
|:-----|:-----|:----------|:---------|
| Ring Attention | 序列并行 + 环形通信 | 4.096M | 32×A100 |
| DeepSpeed-Ulysses | 序列并行 + all-to-all | 1M | 256×A100 |
| ByteScale | 全分片 + 1,024 GPUs | 2M | 1,024 GPUs |
| **LongStraw (Qwen)** | 捕获一次+串行回放 | **4.25M** | **8×H20** |
| **LongStraw (GLM)** | CPU 页面+逐层回放 | 2.1M | **32×H20** |

LongStraw 不以集群规模取胜，而是在固定有限预算下通过架构感知设计达到可比甚至更优的上下文深度。

## 第 2 章 研究背景与动机

### 2.1 问题的核心：AI Agent 对长上下文的需求

AI agent 正从一次性问答向工具调用、代码检查、文档分析和长时间轨迹交互演进。ReAct（Yao et al., 2023a）形式化地将交互视为推理、行动和观察的循环，LongCat-Flash-Thinking（Meituan LongCat Team, 2026）则训练 agent 处理多轮长轨迹。这些 agent 的上下文携带证据、环境观察、工具输出和先前决策。

推理系统正在接近百万 token 上下文——例如 vLLM、TensorRT-LLM 等推理框架已支持长上下文的高效 KV 缓存管理。而后训练工作负载通常停留在 256K token 或以下，依赖长度泛化来部署。这种差距对于 AI agent 尤为重要，因为它们的每个决策都依赖于长历史上下文。

长上下文推理和后训练对内存的使用方式截然不同。推理服务器可以对提示词做一次预填充（prefill），缓存解码所需 KV 状态后丢弃前向计算图，仅保留解码图。后训练则必须对多个响应进行评分并通过它们做反向传播，因此需要同时保留前向图产生的中间激活。

GRPO（Group Relative Policy Optimization, Shao et al., 2024）需要对比共享同一提示词的多个响应。每个响应虽然可能较短（几百到几千 token），但其评分仍然依赖完整的提示词及其缓存状态。对于 $G$ 个响应的分组，全序列 autograd 图需要同时保留 $P + \sum R_i$ 个位置的激活。

最关键的区别在于：在自动微分（autograd）模式下，每个前向计算产生的中间激活必须保留到反向传播完成，而不是在解码后丢弃。这意味着对于 $P$ 个提示词 token 和 $R$ 个响应 token，全序列图需要保留每个 token 的激活。对于 2M+ 上下文，仅激活内存就远超单 GPU 容量。

### 2.2 现有方案及其局限

现有技术从多个方向缓解问题但仍存在差距：

- **FlashAttention** 系列改进了注意力层的数据移动效率，减少了注意力计算的临时内存需求，但不改变梯度图中的激活层存储需求。
- **LoRA/QLoRA** 减少了可训练参数量（Qwen 配置使用 NF4 QLoRA 116.7M 参数），但模型状态和中间激活仍然由全精度基模型产生。
- **激活检查点（Activation Checkpointing）** 以计算换内存，但全序列图的递归结构限制了压缩比。

大规模加速器集群可以通过更广泛的分布来扩展序列长度：
- Ring Attention 在 32 块 A100 GPU 上报告了 7B 模型的 4.096M 位置训练
- DeepSpeed-Ulysses 在 256 块 A100 上实现百万 token 训练
- ByteScale 在 1,024 块 GPU 上报告 2M 位置 LLaMA-7B 案例
- USP 结合了 ring 和 all-to-all 序列并行

这些系统建立了 scale-out 路线。LongStraw 提出一个互补问题：当 GPU 数量固定时，GRPO 执行路径能走多远？

### 2.3 LongStraw 核心思路

LongStraw 通过将长提示词与短响应计算分离来回答这个问题。它在无自动微分（no-grad）模式下一次性评估共享提示词，保存后续 token 所需的条件状态，然后逐个处理响应。反向传播时累积各响应成员的梯度后再调用优化器。

存储的信息遵循模型架构。Qwen3.6-27B 组合了循环层和全注意力层；LongStraw 保留循环状态和上下文分片的 KV 页。GLM-5.2 使用压缩注意力状态、稀疏注意力索引和路由专家；其实现将提示状态移动到 CPU 内存并逐层调入解码器。

LongStraw 运行在 MinT（Mind Lab 训练系统）的训练端。MinT 管理模型 worker、适配器版本和外层策略事务；LongStraw 管理提示状态和一个长上下文事务内部的响应工作。这两个系统处于同一训练栈的不同层次。

### 2.4 GRPO 训练依赖图

GRPO 目标函数的核心是裁剪策略比率代理：

$$\rho_{i,t}(\theta) = \exp\left(\log \pi_\theta(y_{i,t} | x_{1:P}, y_{i,<t}) - \log \pi_{\text{old}}(y_{i,t} | x_{1:P}, y_{i,<t})\right)$$

$$\mathcal{L}_{\text{policy}} = -\frac{1}{G}\sum_{i=1}^G \frac{1}{R_i}\sum_{t=1}^{R_i} \min(\rho_{i,t}A_i, \text{clip}(\rho_{i,t}, 1-\epsilon, 1+\epsilon)A_i)$$

一次组更新的五个逻辑阶段：
1. **提示捕获**：在 $\theta_k$ 下无梯度执行 $x_{1:P}$，保存模型特定的条件状态，释放临时张量。
2. **预步评分**：冻结参数，计算旧策略和参考策略的响应对数概率。
3. **优势构造**：将组奖励转换为 Equation 2 使用的优势值。
4. **策略回放**：逐个重建短响应梯度图，反向传播成员损失后立即释放。
5. **优化器事务**：同步累积梯度，G 个成员后调用一次优化器。

### 2.5 四个证据层次

论文明确区分了四个渐强的证据层次，对读者理解其贡献范围至关重要：

| 层次 | 定义 | LongStraw 状态 | 含义 |
|:------|:-----|:--------------|:------|
| **执行能力** | 所有评分、反向、集合通信和优化器事件是否在所有 rank 上完成 | ✅ 已建立 | 系统运行正常，位级值均为有限 |
| **响应算子保真度** | 分布式回放是否计算了模型定义的条件响应算子 | ✅ Qwen 全部注意力层；⚠️ GLM DSA 仅局部 | Qwen 全注意力通过 CP8 BF16 归约；GLM DSA 选择限制在 CP 分片 |
| **分布式更新一致性** | 所有分片梯度是否归约到正确的参数所有者 | ❌ Qwen K/V adapter 缺失；GLM 跳过 gradient finalization | 当前执行无法保证适配器副本一致 |
| **全梯度等价** | 所有可训练梯度分片是否匹配全序列参考 | ❌ 未测试 | 真正的学习效果等价性未知 |

### 2.6 条件回放与缺失的梯度项

设 $z_P(\theta)$ 为处理提示词后的完整模型状态。全序列损失同时微分显式响应计算和提示状态的参数依赖：

$$\nabla_\theta \ell(\theta, z_P(\theta)) = \left.\frac{\partial \ell}{\partial \theta}\right|_{z_P} + \frac{\partial \ell}{\partial z_P} \frac{\partial z_P}{\partial \theta}$$

当前实现存储 $\bar{z}_P = \text{stopgrad}(z_P(\theta))$ 并仅计算第一项。因此「精确注意力」和「全序列梯度等价」是不同的声明。

## 第 3 章 模型架构分析与瓶颈来源

### 3.1 两个模型轴

LongStraw 实现的两个模型沿两个独立轴分布：FFN 轴（dense vs MoE）和 token mixing 轴（GDN/full-attention vs MLA/DSA）。这些结构差异决定了持久化提示状态和响应时间通信的核心需求。模型层面的标签如「dense」「MoE」或「sparse」掩盖了这种分离。论文的 Figure 3 以示意图形式展示了两个解码器栈在注意力类型、FFN 类型、层计数和通信模式上的差异。

对于 GRPO 训练，这两个轴的叠加效应决定了 GPU 内存瓶颈的具体位置：
- **Dense + full-attention**（如 Qwen）：大量 KV 页面占用 GPU 内存，但显式参数通信简单
- **MoE + sparse-attention**（如 GLM）：专家参数和路由矩阵占用内存，但 KV 存储可以通过 MLA 压缩
- **Dense + sparse-attention** 或 **MoE + full-attention** 尚未实测，但提供了后续研究的配置空间

### 3.2 Qwen3.6-27B：混合循环/注意力 + 密集 FFN

Qwen3.6-27B 配置了隐藏宽度 5,120、64 个解码器层（包括 48 个 GDN 线性注意力和 16 个全注意力层），每层使用密集门控 FFN（中间宽度 17,408）。NF4 QLoRA 微调，可训练参数 116,727,808。

密集门控 FFN 对每个 token 应用相同的三个矩阵（SwiGLU 形式）：

$$F_{\text{dense}}(h) = W_2(\text{SiLU}(W_1 h) \odot W_3 h)$$

**提示状态特征**：GDN 层携带固定形状的循环状态跨提示边界，全注意力层携带随位置数 $P$ 增长的键值页。Qwen 将大部分长上下文存储问题集中到 16 个全注意力层，其余 48 层贡献紧凑的循环状态。对于 16 个全注意力层（4 个 KV 头 × 256 维度，BF16），在 CP8 分片下，每百万额外位置增加：

$$\text{KV 存储/rank} = \frac{10^6 \times 16 \times 2 \times 4 \times 256 \times 2}{8} = 8.192 \text{ GB}$$

这一线性存储斜率解释了在 4M+ 上下文下，即使使用串行回放，仍然有明确的硬件容量上限。

### 3.3 GLM-5.2：MLA/DSA 注意力 + MoE FFN

GLM-5.2 配置了隐藏宽度 6,144、78 个解码器层，KV 和查询潜在宽度分别为 512 和 2,048。多查询潜在注意力（MLA）将每 token 的 KV 内容压缩为潜在表示。稀疏索引器（DSA）有 32 个头，每个头维度 128，每个查询最多选择 2,048 个前置位置：

$$I_{t,s} = \sum_{j=1}^{H_I} w_{t,j}^I \text{ReLU}(\langle q_{t,j}^I, k_s^I \rangle), \quad H_I = 32$$
$$u_t = \text{Attn}(q_t, \{c_s : s \in \text{TopK}(I_{t,:}, 2048)\})$$

其中 21 层为索引计算层，57 层为 IndexShare 层（消费附近源层发布的索引选择）。这种跨层复用类似于 IndexCache 分析的机制，改变了运行时合约：只有 21 个计算层需要持久的索引键页；响应前向必须维护一个 per-forward 的 producer/consumer 持有者。

FFN 方面，前 3 层使用密集 FFN，剩余 75 层使用 256 个路由专家（top-8 + 1 共享专家）：

$$F_{\text{MoE}}(h_t) = F_{\text{shared}}(h_t) + \sum_{e \in \text{Top8}(g(h_t))} p_{t,e} F_e(h_t)$$

一个专家的中间宽度 2,048，三个门控 FFN 矩阵约 3,774 万个权重。256 个路由专家约 96.6 亿参数。在 65,536 token 的 CP 分片下，top-8 路由产生 524,288 个专家 token 行，一个 BF16 缓冲占用 6 GiB。

### 3.4 长提示词的持久化与瞬态状态

| 状态类型 | Qwen | GLM |
|:---------|:-----|:-----|
| **持久化（GPU）** | GDN 循环状态（48 层紧凑），压缩 CP 分片 KV 页（16 层全注意力） | — |
| **持久化（CPU）** | — | MLA 潜在页（78 × 72 MiB），DSA 索引键页（21 × 16 MiB），位置页面元数据 |
| **瞬态（提示捕获后释放）** | 密集 FFN 中间值（17,408 宽度），注意力临时缓冲区 | MoE 路由矩阵（65,536 × 8 专家映射），专家 token 排列，FFN 中间值 |
| **响应时间通信** | 全局 CP8 前向合并（BF16 分子归约），K/V adapter 梯度归约缺失 | EP32 dispatch/combine（8 路专家），DSA CP-local 选择 |

### 3.5 提示词必须和不必须保留的状态

两个模型仍然需要将每个提示词 token 通过每一层。下一层需要输出，即使当前层是稀疏或循环的。容量提升来自张量生命周期：密集 FFN 中间值、MoE 路由、专家 token 排列、注意力临时空间和适配器激活可以在提示词捕获后立即死亡。只有后续响应 token 依赖的条件状态才存活。

## 第 4 章 LongStraw 执行设计

### 4.1 核心规则：一次性捕获，后缀回放

LongStraw 遵循一条规则：仅当后续响应 token 依赖一个张量时才将其保留跨提示边界。该规则适用于物理分配（而非仅张量逻辑视图），并将算子所需的状态与产生该状态时所需的临时缓冲区分开。预算受约束意味着固定加速器数量加上每设备 H20 内存限制（8 块 H20 用于 Qwen，32 块用于 GLM）。

### 4.2 一次更新交易的四个阶段

**Phase 1：提示捕获**。在 $\theta_k$ 下无梯度执行 $x_{1:P}$。在每层保存模型特定的提示状态并释放临时隐藏张量、注意力临时缓冲区、FFN 激活和 MoE 路由缓冲。

**Phase 2：预步评分**。将完成的提示状态视为只读。在策略反向传播前计算旧策略和参考策略的响应对数概率。参数在整个组中保持固定。GLM 在回放前冻结两个分数集；Qwen 使用成员串行的 old/reference/policy 调度。

**Phase 3：策略回放**。逐个重建短当前策略响应路径（autograd）。重用相同的只读提示状态，反向传播成员损失后立即释放该成员图。

**Phase 4：优化器事务**。在所有 G 个反向后保留累积的局部梯度，每个 worker 调用一次优化器。捕获状态现在相对于更新后的参数已过期。

### 4.3 内存与时间的权衡

活动计算图的内存占用量从 $P + R$ 缩小到 $R$：

$$M_{\text{live}} \approx M_{\text{fixed}} + M_{\text{prompt}}(P) + M_{\text{grad}} + \max_i M_{\text{branch}}(R_i) + M_{\text{score}}\left(\sum_i R_i\right)$$

$$T_{\text{update}} = T_{\text{prompt}}(P) + \sum_{i=1}^G T_{\text{score+replay}}(R_i)$$

活动策略图由最大成员而非成员数量限定。Equation 9 不使总内存在 $G$ 上常数：输入/标签对象、奖励和冻结评分仍然为 $O(G)$ 或 $O(\sum_i R_i)$。但串行回放将分组规模从内存维度转变为调度和时间维度。

### 4.4 状态所有权与放置策略

Qwen 将紧凑的 GDN 和 KV 状态保留在 GPU 上，因为 8 路上下文并行使每个 rank 的状态可容纳，且响应注意力合并需要反复读取所有分片。每个保留的页分片被复制到大小正确的物理分配中，避免保留父分配中其他视图的不可释放问题。

GLM 将 CP-local 的 MLA 和索引键页保留在 CPU 上。响应回放时，逐层将所需页面调入 GPU，执行该短响应层后释放或归位。CPU 放置以传输时间换取受限驻留，仅在回放逐层进行时有用。复制完整的 78 层前缀回 GPU 会重建存储峰值。

### 4.5 全层检查点

GLM 实现使用全层检查点保存回放层的中间激活。全局 RoPE 缓存避免为每一层和分支重建位置张量。对于 78 层的解码器栈，这避免了在回放过程中保留完整的响应层激活链。

## 第 5 章 实验结果与分析

### 5.1 Qwen：密集混合回放（8×H20）

**执行配置**：固定 8 块 H20 GPU，CP8（8 路上下文并行），NF4 QLoRA 116,727,808 可训练参数。64 层解码器包括 48 个 GDN 循环层和 16 个全注意力层。

**执行配置**：固定 32 块 H20 GPU，TP1/CP32/EP32，78 层解码器。21 个索引计算层 + 57 个 IndexShare 层。3 密集 + 75 MoE（256 专家，top-8 + 1 共享）。

**容量里程碑**：

| 里程碑 | 上下文长度 | 耗时（s） | 说明 |

### 5.5 Qwen 执行深化分析

**4.25M 运行的时间分解**：在 4.25M G=8 运行中，共享前缀捕获占 81.3%（17,697.213 s / 21,750.133 s），后缀回放占 18.7%。相比之下，2.1M G=2 运行中前缀占 89.6%（4,656.225 s / 5,198.780 s）。上下文越长，前缀占比越高，因为 KV 页面存储和捕获时间随上下文线性增长。

**响应回放块设计**：Qwen 实现将 8,192 个响应位置分为 4 个 2,048 位置的块逐个回放。每块完成后释放反向图，确保活动内存始终由块长度而非总响应长度决定。即使在分离前缀路径下，保留的 FFN 中间值和注意力临时缓冲也绑定到块大小。

**4.25M 线性扩展验证**：Qwen 在 2.1M 和 4.25M 上下文处的峰值内存遵循预期线性扩展。在 CP8 下，KV 页面每百万位置增加 8.192 GB/rank，与理论推算一致。4,456,448 位置的完整 G=8 回放验证了此斜率在系统实现中的可预测性，表明更大上下文（如 8M）在相同硬件上不可行（8M 时仅 KV 页就需要 ~65 GB/rank）。

**分离前缀路径 vs 提示适配路径**：提示适配路径（保留完整梯度图）在 4.25M 的策略反向 OOM，而分离前缀路径（pruned gradient pages）成功。两者的内存差异来自 dK/dV 梯度页的修剪：提示 KV 页仍参与注意力和 dQ 计算，但自身 unused 的 dK/dV 存储被从活动图中移除。

## 第 6 章 固定预算系统经验教训

### 6.1 容量来自生命周期而非稀疏性

LongStraw 的核心发现是：固定预算下的容量提升主要来自张量生命周期的管理，而非仅靠注意力稀疏性。MoE 路由和稀疏注意力（DSA top-2048）不能自动解决内存问题——GLM 的全序列图因 DSA 评分临时空间（64 GiB FP32）、MoE 后处理（FC2 matmul 11.7 GiB）和专家输出拼接（19.37 GiB）而 OOM，尽管每 token 仅激活 8/256 专家且注意力稀疏。LongStraw 通过将 MLA/DSA 页面放置在 CPU、逐层调入并全层检查点来突破这些限制。

### 6.2 物理所有权属于算法设计

张量的物理放置决定了通信模式和正确性边界：
- Qwen 将 KV 页放在 GPU 上 → 实现 CP8 全局注意力合并 ✅，但 rank 局部 dK/dV 梯度未归约导致适配器副本不一致 ❌
- GLM 的 CPU 页面放置 → 避免 GPU 内存峰值 ✅，但 CP 分片局部 DSA 选择不进行跨 rank 归约 ❌

张量生命周期、设备放置和正确性边界是相互绑定的，必须在系统设计时同时考虑。

### 6.3 Dense 与 MoE 将峰值移动到不同位置

密集 FFN（Qwen）的峰值压力在注意力 KV 页面和临时缓冲区。MoE（GLM）的峰值压力在专家 token 排列、FC2 矩阵乘法和 DSA 评分临时空间。这要求固定预算方案必须针对具体模型结构定制：对 Qwen 有效的方法（GPU 上保留 KV 页面）不适用于 GLM（CPU 上保留 MLA 页面 + 逐层调入）。

### 6.4 上下文与专家并行是正交的

GLM 在同一 32 块 GPU 上折叠 CP32 和 EP32：上下文并行解决注意力状态存储，专家并行解决 MoE 参数驻留。这两个维度解决不同的所有权和通信问题，不能互相替代。CP 不减少专家计算，EP 不减少注意力存储。

### 6.5 分组规模是调度结果而非内存问题

Qwen 实验数据显示，分组规模 G=2→G=8 的内存增量仅 0.208 GB（0.213%），因为共享提示词的前缀捕获占据了总执行时间的约 89.6%（G=2）且内存开销在所有成员间共享。

### 6.6 响应回放的块分解设计

Qwen 实现将较长响应分解为 2,048 位置的固定块进行回放。每块完成后释放前向和反向的中间激活。这种设计使活动内存绑定到块大小而非总响应长度，对长响应（如 8,192 位置的 agent 轨迹）尤为重要。在 Qwen 的 4.25M G=8 运行中，8,192 位置的响应被分解为 4 个 2,048 块的序列。每块完成包含：前向传播 → 损失计算 → 反向传播 → 梯度累积 → 块释放。

块内通信模式：在 CP8 下，每块的全注意力计算仍需要跨 rank 的 LSE/输出合并（BF16 分子归约）。块分解本身不改变跨 rank 通信模式，但显著减少了每 rank 的峰值激活内存。

### 6.7 GLM 的层回放设计

GLM 实现采取不同的分解粒度——逐层而非逐块。在响应回放阶段，每次仅将一个解码器层的 MLA 和 DSA 页面从 CPU 调入 GPU。单层执行完成后，检查点保存输出并释放 GPU 层状态，再调入下一层。这种设计利用了 GLM 的深堆栈结构（78 层），将 GPU 活动内存从完整的 78 层响应计算图压缩到单层响应计算。

### 6.8 批处理评分的负结果

批处理 old/reference 评分在 4K 响应时有效（单 GPU 总时间从 17.529 降至 14.528 秒），但在 4.46M 上下文时仅节省 0.7% 时间（4051.240 → 4024.290 秒），同时峰值内存从 83.894 飙升至 135.128 GB。这表明在超长上下文下，评分批处理的内存成本远超时间收益，对长上下文训练而言优先级较低。

### 6.9 四层证据框架的系统设计价值

论文将验证分为四个层次（执行能力→算子保真度→分布式一致性→全梯度等价），这种透明分层的做法在 ML 系统论文中少见。它避免了将「系统成功运行」误报为「训练正确有效」的常见陷阱，并为后续工作提供了明确的改进方向标。

### 6.10 当前路径的未验证项

当前报告明确声明以下几点未完成：
1. 分布式梯度组合不完整（Qwen 缺少 K/V adapter 梯度归约，每 rank 的 AdamW 实例独立运行）
2. 提示状态梯度被截断（Equation 3 的第二项 $\frac{\partial \ell}{\partial z_P}\frac{\partial z_P}{\partial \theta}$ 缺失）
3. GLM 的 DSA 注意力保持在 CP 分片局部（65,536 token），未达到全局 2.1M 全上下文保真度
4. 工作负载是执行探针，不包含在线生成和奖励模型执行

## 第 7 章 局限性与延伸阅读

### 7.1 主要局限

1. **分布式梯度组合不完整**：Qwen 路径中，分布式注意力反向会 all-reduce dQ，但返回页面所有者的 dK/dV——这些梯度是分片 KV 张量的正确梯度，但它们的投影适配器是复制的，每次创建 AdamW 实例时未使用 DDP 或参数梯度归约器。GLM 自定义驻留组循环在正常 Megatron 调度外运行反向，跳过了 `finalize_model_grads` 调用，CP 复制的非专家适配器从未归约的局部梯度上步进。

2. **历史 GLM 接收使用 CP-局部响应注意力**：DSA 的 top-2,048 选择保持在 65,536 token 的 CP 分片局部。虽然页面按 zigzag 顺序分配给 32 个 rank，但每个 rank 的稀疏选择仅覆盖其本地分片。论文指出：»the selected 2,048 positions define the operator, not merely its memory layout«——当前 GLM 路径实际上改变了算子定义。

3. **提示状态梯度被截断**：`stop_grad(z_P(θ))` 丢弃了完整梯度项。使用条件响应反向传播无法恢复全序列梯度等价。即使 Qwen 的全注意力回放在算子水平上精确，其反向梯度在语义上不等价于全序列训练。

4. **工作负载是执行探针**：使用提供的确定性响应和奖励（不包含在线生成和奖励模型执行），仅覆盖训练的图部分，不覆盖完整训练循环。论文明确声明 »it exercises prompt capture, frozen scoring, live policy backward, group accumulation, and optimizer execution, but excludes online generation and reward-model execution«。

5. **资源和可复现性差距**：H20 GPU 独占访问、软件栈手动配置和分布式调试基础设施限制了外部复现。论文提供配置和容器文件，但分布式 GPN 环境的精确再现需要大幅投入。

### 7.2 验证路线图

论文提出明确的四步验证顺序：
1. **分布式梯度审计**：per-module hook coverage、梯度计数 counts、哈希值 hashes 和梯度 deltas，确认每层梯度的完整通信路径。当前代码仓库的 `STATUS.md` 跟踪了具体阻塞项，包含需要修复的分布式通信模式。
2. **逐参数梯度对比**：在短上下文下运行全序列和回放路径（两者都适配），逐参数对比梯度张量。这是区分「系统成功执行」和「训练正确性」的关键实验。
3. **在线扩展**：扩展到在线生成和奖励模型执行，包含完整的 GRPO 训练循环（响应生成 → 奖励评分 → 策略更新 → 重新捕获）。
4. **完整训练循环**：重复训练循环（recapture → update → recapture），验证状态过期后的重捕获收敛性。

### 7.3 相关工作

LongStraw 与以下领域相关联：
- **Scale-out 长上下文训练**：Ring Attention（4.096M on 32 A100s）、DeepSpeed-Ulysses（1M on 256 A100s）、ByteScale（2M on 1,024 GPUs）、USP
- **训练系统**：MinT（管理模型 worker、适配器版本和外层策略事务）、Megatron-LM
- **高效注意力**：FlashAttention 系列、MLA（DeepSeek-AI）、DSA、GQA、IndexCache
- **MoE 训练**：TP/EP/CP 多维并行、Megatron-Core 调度
- **内存优化**：激活检查点、PEFT（LoRA/QLoRA）、量化训练
- **GRPO 系统**：GRPO（Shao et al., 2024）、Open R1 训练栈

LongStraw 在系统的独特定位：它不追求新的规模记录（scale-out），而是在固定预算下探索 GRPO 的可行执行极限（fixed-budget），并提供从执行能力到全梯度等价的分层验证框架。这种方法明确区分了系统可行性（execution capacity）和训练正确性（full-gradient parity），为长上下文后训练系统的工程实现提供了参考框架。

### 7.4 对后续研究的启示

LongStraw 的明确贡献不在于大规模训练记录，而在于提供了四条对后续系统设计有直接影响的经验：

1. **分层验证框架**：四层证据体系（执行能力→算子保真度→分布式一致性→全梯度等价）可直接复用于评估任何长上下文训练系统。当前许多系统仅报告「训练损失下降」或「吞吐量」，而不区分执行可行性（系统成功运行）和训练正确性（梯度等价于全序列训练）。

2. **架构感知设计原则**：固定预算下的系统设计必须深入理解目标模型的内存访问模式。Qwen 和 GLM 截然不同的存储和通信需求说明，不存在通用的固定预算方案——系统设计需要与模型架构耦合。

3. **CPU 页面 + 逐层调用的工程范式**：GLM 的 CPU 页面方案为超大模型的固定预算训练提供了范式参考：在注意力状态可以压缩（MLA）且无需全图 context 时，CPU 驻留 + 按需调度的混合执行是可行的。

4. **开源基础设施**：代码仓库作为 MinT 项目的一部分开源，提供了分布式训练栈的参考实现（含容器、配置、运行 tracelog），降低了复现门槛。
