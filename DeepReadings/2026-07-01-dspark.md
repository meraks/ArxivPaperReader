## Ch1 论文概述与核心贡献

### 1.1 自回归解码的延迟瓶颈

主流 LLM 采用自回归（autoregressive）解码：每生成一个 token 都要执行一次完整的前向传播（forward pass），单 token 的服务延迟随已生成序列长度近似 $O(n)$ 增长。在交互式、高并发的推理服务场景下，这种"逐 token 串行"成为吞吐与延迟的核心瓶颈——target 模型的大部分算力消耗在重复处理同一不断增长的 KV 缓存上，而非生成新内容。

### 1.2 推测解码：以并行验证换取延迟下降

推测解码（speculative decoding）将"生成"与"验证"解耦：

1. 一个轻量 **draft 模型** 廉价地提出一段候选 token 块（$\gamma$ 个）；
2. **target 模型** 用单次前向并行验证整块；
3. 通过 **拒绝采样（rejection sampling）** 接受 target 分布一致的 token，保证最终输出分布与纯自回归解码 **完全无损（lossless）**。

由于验证整块的成本接近生成单 token，只要 draft 质量足够高、块内接受长度 $\tau$ 足够大，就能换取接近线性的端到端加速。

### 1.3 并行 drafter 的两个瓶颈

**并行 drafter**（如 DFlash）能在单次前向中一次性产出全部 $\gamma$ 个候选 token，使 draft 阶段开销 $T_{\text{draft}} \approx O(1)$，理论上限更高。但论文指出它面临两个相互独立、但同样致命的瓶颈：

- **Suffix decay（尾部衰减）**：并行 drafter 的各位置 token 是 **独立预测** 的，缺乏 token 间的条件依赖。块首因直接以真实上下文为锚尚可，但越往块尾，候选分布与真实自回归分布偏离越大，接受率迅速衰减，$\tau$ 被压低。
- **盲目验证浪费批容量**：高并发服务中，target 验证器的批容量（batch capacity）由所有并发请求共享。若不加区分地把完整 spec 块（含高拒绝风险的尾部 token）全部送入验证，会挤占本可服务其他请求的容量，严重拖累整体吞吐——这正是生产环境真正在意的指标。

### 1.4 DSpark 的双重机制

DSpark 针对上述两个瓶颈，提出两个正交互补的机制：

1. **半自回归生成（Semi-Autoregressive Generation）**——治 suffix decay。
   以 **DFlash 式并行骨架** 承担主体计算（$T_{\text{draft}}$ 几乎 $O(1)$），再叠加一个 **轻量顺序头**（sequential head），为块内 token 注入依赖建模，使尾部 token 的预测能够感知前序已生成内容，从而抑制 suffix decay。（具体形式见第三章 Eq 4–6。）

2. **置信度调度验证（Confidence-Scheduled Verification）**——治批容量浪费。
   一个 **置信度头** 估计每个位置的"前缀存活概率"，再由 **硬件感知前缀调度器**（Algorithm 1）结合引擎实测的吞吐曲线，按当前系统负载为每个请求 **动态裁剪** 验证长度——高负载时主动缩短高拒绝风险请求的验证，把容量让给更可能存活的请求，且裁剪过程以 early-stopping 维持 **无损保证**。（具体形式见第三章 Eq 7–8 与 Algorithm 1。）

## Ch2 推测解码背景

### 2.1 标准推测解码的延迟模型

一次推测解码迭代的端到端延迟可分解为 draft 与 verify 两阶段之和，再除以本轮被接受（ survive ）的 token 数 $\tau$（accepted length）：

$$
L = \frac{T_{\text{draft}} + T_{\text{verify}}}{\tau}
$$

直觉很直接：分母 $\tau$ 越大（一次验证接受越多），单位延迟产出越多；分子越小（draft 越快、verify 越省），单轮越廉价。所有加速技术本质上都在动这两项。

### 2.2 接受规则：拒绝采样与"首拒则止"

设第 $k$ 个位置上，target 模型与 draft 模型给出的下一个 token 分布分别为 $p^t_k$、$p^d_k$。对 draft 提出的候选 $x_k$，按以下概率接受：

$$
a_k = \min\left(1,\; \frac{p^t_k(x_k)}{p^d_k(x_k)}\right)
$$

验证严格 **从左到右** 进行：一旦某位置被拒绝，该位置及其后所有 token 全部丢弃，验证 **即刻停止**（首拒则止）。被拒绝位置由 target 分布重新采样补齐，从而保证最终输出分布与纯自回归解码 **逐 token 无损**。这一"首拒则止"规则直接解释了 suffix decay 为何致命——块尾接受率低，意味着尾部 token 几乎必然被拒、$\tau$ 被钉死在块首附近。

### 2.3 加速的三杠杆

回到延迟公式 $L=(T_{\text{draft}}+T_{\text{verify}})/\tau$，提升加速比的三条正交路径（也是后续工作的分类轴）：

1. **更快的 draft**（减小 $T_{\text{draft}}$）——更轻量的 draft 模型 / 更少的前向开销；
2. **更好的 draft**（增大 $\tau$）——提升 draft 与 target 的分布吻合度，推迟首次拒绝；
3. **更聪明的验证**（减小 $T_{\text{verify}}$ 的有效成本）——树验证、长度自适应、按置信度调度等系统侧优化。

DSpark 的两个机制分别落在杠杆 2（半自回归提 $\tau$）与杠杆 3（置信度调度省验证）上。

### 2.4 自回归 drafter：以 Eagle3 为代表

自回归 drafter 自身仍按 token 顺序逐步生成，因此其 draft 耗时随块长线性增长：

$$
T_{\text{draft}} \propto \gamma
$$

这迫使实践采取两个妥协：

- **小 $\gamma$**：块长不能太大，否则 $T_{\text{draft}}$ 抵消加速收益；
- **浅层 draft**：为压低单步开销，draft 层数必须很少（如 Eagle3 仅 **1 层**，见 Sec 4.1）。

为弥补小 $\gamma$ 下 $\tau$ 偏低，自回归 drafter 普遍引入 **树验证（tree verification）**：在单次 verify 前向中同时验证一棵候选树，扩大并行覆盖。但树结构增加了验证张量的规模与计算量，在高并发服务中会进一步挤压批容量。

### 2.5 并行 drafter：以 DFlash 为代表

并行 drafter 的核心思想是 **在单次前向中一次性产出全部 $\gamma$ 个候选 token**，从而把 $T_{\text{draft}}$ 压到几乎与 $\gamma$ 无关（接近 $O(1)$）。DFlash 的实现要点：

- **上下文特征提取**：从 target 模型获取上下文表示作为 draft 的输入锚点；
- **KV 注入（KV injection）**：将 target 的 KV 信息注入 draft 主干，使其在一次前向内并行生成全部 $\gamma$ 个位置（原文 Eq 2–3）；
- **锚点 + mask token 输入**：输入序列由锚点 token 与 $\gamma$ 个 mask token 拼接而成，draft 在 mask 位置并行预测各候选 token；
- **替换 embedding 与 LM head**：draft 复用 target 的 embedding 层与 LM head，使输出空间对齐 target 词表。

**优势**：$T_{\text{draft}}$ 与 $\gamma$ 解耦，因此可采用 **更深的 draft**（DFlash 用 **5 层**）与 **更大的 $\gamma$**，单块潜在覆盖远超自回归 drafter。

**劣势（即 suffix decay 的根源）**：各位置预测 **相互独立**，块内无 token 间条件依赖，尾部 token 的边缘分布偏离真实自回归联合分布；尤其当多个合理续写路径并存时，独立预测易产生"多模态碰撞"（不同位置各自选了相互不一致的分支），进一步压低尾部接受率。这正是 DSpark 半自回归机制要解决的问题——在不放弃并行性的前提下，把块内依赖重新引入。

## Ch3 半自回归 Draft 架构

DSpark 的核心设计目标是：在不放弃并行生成 $O(1)$ 延迟优势的前提下，恢复块内 token 间的依赖关系，从而抑制并行 drafter 固有的 **suffix decay**（尾部 token 与前缀脱节、互相矛盾）。其实现是一条「并行骨架 + 轻量序列头」的两阶段通路。

### 3.1 设计动机

推测解码的每 token 延迟可写成

$$
L = \frac{T_{\text{draft}} + T_{\text{verify}}}{\tau},
$$

其中 $\tau$ 为每步平均接受长度。最小化 $L$ 的两条路径同时成立：既要提高 $\tau$，又要压低 $T_{\text{draft}}$。现有 drafter 在这两端之间存在根本性的取舍：

- **自回归 drafter（代表：Eagle3）。** 每个 draft token 都条件于其前驱 token，因此序列连贯、$\tau$ 高。但生成 $\gamma$ 个 draft token 需要 $\gamma$ 次串行前向，即 $T_{\text{draft}} \propto \gamma$。为控制延迟，Eagle3 被迫采用极浅结构（仅 1 层，见 §4.3）并配合较小的 $\gamma$，再用树验证（tree verification）补充接受长度——而树验证本身会增加单步验证量。
- **并行 drafter（代表：DFlash）。** 单次前向即可并行生成全部 $\gamma$ 个 draft token，$T_{\text{draft}} = O(1)$，因此可以使用更深的网络（5 层）和更大的 $\gamma$。其代价是：每个位置被**独立**预测，块内不存在 token 间依赖，导致尾部 token 缺乏前缀约束，出现 suffix decay。

两者的对立表明，真正理想的 drafter 应同时具备「并行的低延迟」与「自回归的依赖建模」。DSpark 的解法是**两阶段半自回归**：让并行骨架承担绝大部分计算（保持 $T_{\text{draft}}\approx O(1)$），再叠加一个轻量序列模块为每个位置注入对前驱 token 的依赖。

### 3.2 并行阶段

并行阶段直接基于 DFlash 骨架，但对其输入布局做了一处关键改造：**将 anchor token 作为第一个预测位置**。具体地：

- 输入侧：送入 $\gamma$ 个位置（anchor + 后续位置），经 DFlash 的 KV 注入与 mask 机制（Ch2 中的 Eq 2–Eq 3），单次前向得到全部位置的表达。
- 输出侧：对每个位置 $k\in\{1,\dots,\gamma\}$，并行骨架产出两样东西：
  1. **隐藏状态** $h_k$（后续供置信度头复用）；
  2. **基础 logits** $U_k$。

$U_k$ 是「无视块内依赖」的独立预测，本身已比纯并行 DFlash 多了 anchor 的条件信息，但仍未引入 $x_{k-1}$ 的依赖。补全依赖的工作交给下一阶段。

### 3.3 序列阶段

序列阶段用一个加性 bias $B_k$ 修正基础 logits，使最终分布呈现自回归式的因式分解（**Eq 4**）：

$$
p_k(v) = \frac{\exp\bigl(U_k(v) + B_k(v)\bigr)}{\sum_{v'}\exp\bigl(U_k(v') + B_k(v')\bigr)}.
$$

bias $B_k$ 的作用是把「前驱 draft token」的信息注入位置 $k$ 的预测，从而在保持并行骨架不变的前提下引入块内依赖。论文给出两种 $B_k$ 的参数化：

**Markov head（Eq 5，默认）。** $B_k$ 仅依赖前一个 token $x_{k-1}$，并采用低秩双线性形式：

$$
B_k = W_1[x_{k-1}]\,W_2, \qquad W_1\in\mathbb{R}^{V\times r},\; W_2\in\mathbb{R}^{r\times V},\; r=256.
$$

低秩（$r=256$）使额外参数与计算量极小。其作用在于消除并行预测中的「语义/语域碰撞」：例如对致谢的回复，并行 head 仅凭 anchor 无法区分 *"you're welcome, of course"* 与 *"you're welcome, no problem"* 这类不同语域的延续，基础 logits 给出的是两者的混合分布；Markov head 通过条件于前一个 draft token，将分布偏移到与已选语域一致的方向，从而消除碰撞。由于仅依赖单步前驱，它可以在并行前向后用一次极廉价的查表式修正完成。

**RNN head（Eq 6）。** 引入门控循环状态 $s_k$ 累积**完整前缀**历史：

$$
s_k = g(s_{k-1}, x_{k-1}), \qquad B_k = f(s_k),
$$

理论上能建模任意长度的块内依赖。但实验表明它相对 Markov head 仅带来**边际提升**，而 Markov head 已足以消除绝大部分 suffix decay。因此 DSpark 默认采用 Markov head，RNN head 仅作可选项。

**轻量性验证。** 这一序列阶段几乎不增加延迟：在 $\gamma$ 从 4 增到 16 的范围内，顺序头带来的延迟开销仅为 **0.2%–1.3%**（Fig 4）。这印证了 §3.1 的设计前提——「并行骨架 + 轻量序列头」确实把依赖建模的成本压到了可忽略的水平，从而保留了并行 drafter 的 $O(1)$ 优势。

## Ch4 置信度调度验证

仅有高质量 draft 还不够。在高并发服务系统中，盲目验证长 draft 块会把宝贵的批容量浪费在高拒收风险的 token 上，反而拖垮吞吐。DSpark 的第二根支柱是**置信度调度验证**：先用置信度头估计每个位置的条件接受概率，再用硬件感知调度器按系统负载动态裁剪每条请求的验证长度。

### 4.1 置信度头

**置信度估计（Eq 7）。** 对位置 $k$，置信度头复用并行阶段的隐藏状态 $h_k$ 与 Markov head 的嵌入 $W_1[x_{k-1}]$（参数共享），输出一个标量条件接受概率：

$$
c_k = \sigma\!\left(w^\top\bigl[h_k;\; W_1[x_{k-1}]\bigr]\right) \in (0,1).
$$

这里 $c_k$ 解释为「给定前 $k-1$ 个位置已被接受、位置 $k$ 被（拒绝采样）接受的条件概率」。

**监督信号（Eq 8）。** 置信度头不依赖人工标注，而是用 draft 分布 $p^d_k$ 与 target 分布 $p^t_k$ 的总变差距离构造软标签：

$$
c^*_k = 1 - \tfrac{1}{2}\,\bigl\|p^d_k - p^t_k\bigr\|_1 \;\in[0,1].
$$

该量的物理含义是两分布的重叠度：$p^d_k$ 越接近 $p^t_k$，$c^*_k$ 越接近 1，对应越高的接受概率。它天然落在 $[0,1]$，可直接作为回归/BCE 目标。

**STS 校准。** 未经校准的置信度头存在系统性偏差，原始 ECE 高达 **3%–8%**。由于 §4.2 的无损调度严格依赖 $c_k$ 的准确性（误校准会导致错误的截断决策），论文采用 **STS（Stepwise Temperature Scaling）**：对每个位置从左到右做一次一维温度缩放。校准后 ECE 降至约 **1%**（Fig 6）。

**有效性佐证。** Fig 5 的阈值扫描显示，仅靠对校准后的 $c_k$ 设阈值，chat 域的接受率即可从 **45.7%** 调到 **95.7%**，说明该置信度信号确实携带了与拒收风险强相关的信息，足以驱动后续调度。

### 4.2 硬件感知调度器

调度器的任务是在给定批容量下，决定每条请求 $r$ 应验证到第几个位置，以最大化**系统级**吞吐。

**存活概率。** 定义请求 $r$ 的 draft 存活到位置 $j$（即前 $j$ 个位置全部被接受）的概率为各位置条件接受概率的乘积：

$$
a_{r,j} = \prod_{i\le j} c_{r,i}.
$$

$a_{r,j}$ 越大，意味着继续验证位置 $j$ 越可能产生有效接受、而非浪费批容量。

**优化目标。** 调度器最大化系统吞吐

$$
\Theta = \tau \cdot \mathrm{SPS}(B),
$$

其中 $\tau$ 为平均接受长度，$\mathrm{SPS}(B)$ 为批 $B$ 下引擎每秒步数（system steps per second）。两者存在张力：验证更长 → 单请求 $\tau$ 更高，但占用更多批容量 → 高并发下 $\mathrm{SPS}(B)$ 下降。调度器正是在这一 Pareto 权衡上寻优。

**Algorithm 1（贪心 + early-stopping）。**

1. 对批内所有 $(r, j)$ 二元组计算存活概率 $a_{r,j}$；
2. 按 $a_{r,j}$ **全局排序**；
3. **贪心地逐个添加**（请求，位置）对进入验证，直到批容量耗尽；
4. **提前停止（early-stopping）**：一旦继续添加在当前负载下不再提升 $\Theta$，立即停止。

**无损保证的关键。** 推测解码的无损性来自拒绝采样：验证 token $x_k$ 时按 $\min(1,\,p^t_k(x_k)/p^d_k(x_k))$ 接受，可保证输出分布严格等于 target 分布。置信度调度对验证窗口做了**截断**（位置 $>J_r$ 不再验证，直接退回 target 自回归解码），这本身是无损的——前提是截断点的选择不能与验证结果（接受/拒绝）相关联，否则会引入 selection bias、扭曲输出分布。Algorithm 1 的全局排序 + early-stopping 恰好满足这一条件：所有请求的截断点是基于存活概率估计**一次性、全局地**决定的，与具体接受/拒绝结果解耦，因而保持分布不变。

**Appendix A 反例。** 论文在附录中给出反例：若去掉 early-stopping、改用逐请求在线自适应截断（根据已发生的接受结果决定是否继续验证），则会破坏上述解耦，违反无损保证。这从反面说明了 early-stopping 在调度器中不可省略。

### 4.3 训练

DSpark 的训练目标是同时学出「好 draft」与「准置信度」。

**联合损失（Eq 9–12）。** 总损失为三项加权和：

$$
L = 0.1\cdot L_{\text{ce}} + 0.9\cdot L_{\text{tv}} + 1.0\cdot L_{\text{conf}},
$$

各项含义：
- $L_{\text{ce}}$：draft 分布相对真值的交叉熵；
- $L_{\text{tv}}$：draft 分布 $p^d$ 与 target 分布 $p^t$ 的总变差距离，直接拉近 draft 与 target；
- $L_{\text{conf}}$：置信度头相对软标签 $c^*_k$（Eq 8）的监督损失。

权重 $\alpha_{\text{ce}}=0.1$、$\alpha_{\text{tv}}=0.9$、$\alpha_{\text{conf}}=1.0$ 表明：训练更重视「分布匹配」而非单纯的硬标签拟合，并对置信度头给予最高权重（因为它直接决定下游调度的质量）。

**位置权重。** 由于位置 $k$ 只有在其前 $k-1$ 个位置全部被接受后才会真正生效，训练时按存活倾向对损失加权：

$$
w_k = \exp\!\left(-\frac{k-1}{\gamma}\right).
$$

位置 1（$k=1$）权重为 $1.0$，越靠后的位置权重越小，使优化聚焦于「最常被验证到」的前部位置。

**架构与数据。** 训练全程**冻结 target 模型**，仅更新 draft 模型与各 head。DSpark 的 draft 模型为 **5 层**（与 DFlash 同等深度，远深于 Eagle3 的 1 层），训练数据为 **Open-PerfectBlend**，共 **1.3M** 条样本。这些设置共同支撑了 §3 中并行骨架的容量与序列头的低秩轻量修正。

## Ch5 实验结果与分析

### 5.1 实验设置

**目标模型（Target）**：Qwen3-4B、Qwen3-8B、Qwen3-14B、Gemma4-12B，覆盖中小参数量级与两个模型族。

**Drafter 对比**：三种代表性 drafter，控制变量一致——

| Drafter | 层数 | 范式 |
|---------|------|------|
| Eagle3 | 1 层 | 自回归（autoregressive），$T_{\text{draft}} \propto \gamma$ |
| DFlash | 5 层 | 并行（parallel），单前向生成整块 |
| **DSpark** | 5 层 | 半自回归（semi-autoregressive） |

**训练配置**：基于 **Open-PerfectBlend** 的 **1.3M 样本**，训练 **10 epochs**，目标模型置于 **non-thinking mode**（避免推理链干扰、统一比较口径）。三组 drafter 在相同数据与训练预算下公平训练。

**评估协议**：共 **9 个 benchmark**，划分为 **3 个领域**——
- **Math**：GSM8K、MATH500、AIME25
- **Code**：MBPP、HumanEval、LCB
- **Chat**：MT-Bench、Alpaca、Arena-Hard

主指标为 **离线接受长度 $\tau$**（accepted length），即每个 verify step 平均被目标模型接受的 token 数，对应解码延迟公式 $L = (T_{\text{draft}}+T_{\text{verify}})/\tau$ 中的分母——$\tau$ 越大，单次前向摊到的有效 token 越多，延迟越低。

### 5.2 主结果（Table 1）

DSpark 在 **全部目标模型 × 全部 benchmark** 上同时超越自回归基线 Eagle3 与并行基线 DFlash。下表嵌入 **Table 1 的 Qwen3-4B 行**（9 个 benchmark 完整逐项数值）：

**Table 1（Qwen3-4B，离线接受长度 $\tau$）**

| Drafter | GSM8K | MATH500 | AIME25 | MBPP | HumanEval | LCB | MT-Bench | Alpaca | Arena-Hard |
|---------|-------|---------|--------|------|-----------|-----|----------|--------|------------|
| Eagle3（1层） | 5.14 | 4.62 | 3.92 | 3.69 | 4.16 | 3.77 | 2.39 | 2.26 | 2.55 |
| DFlash（5层） | 5.40 | 4.85 | 4.15 | 4.40 | 4.74 | 4.18 | 3.07 | 2.96 | 2.83 |
| **DSpark（5层）** | **6.11** | **5.70** | **4.89** | **5.13** | **5.38** | **4.86** | **3.64** | **3.54** | **3.29** |

按 9 个 benchmark 的 **macro-平均** 计算相对提升（值取自 Table 1，经核验）：

| 目标模型 | DSpark vs Eagle3 | DSpark vs DFlash |
|----------|------------------|------------------|
| Qwen3-4B | **+30.9%**（3.611 → 4.727） | **+16.3%**（4.064 → 4.727） |
| Qwen3-8B | **+26.7%**（3.798 → 4.813） | **+18.4%**（4.067 → 4.813） |
| Qwen3-14B | **+30.0%**（3.676 → 4.779） | **+18.3%**（4.039 → 4.779） |

**关键观察**：DSpark 对两类基线的优势在 14%–31% 之间且**跨规模稳定**——无论 4B 还是 14B，半自回归 + 置信度调度带来的增益不会随目标模型变大而消失，说明瓶颈在于 drafter 架构与验证策略，而非目标容量。

**Domain effect（领域效应）**：DSpark 的 $\tau$ 在三个领域呈分层结构，**math > code > chat**：

$$\text{math}\ (4.9\text{–}6.2) \;>\; \text{code}\ (4.9\text{–}5.5) \;>\; \text{chat}\ (3.2\text{–}3.7)$$

math/code 这类 **结构化、长程可预测** 的任务上 draft 接受率天然更高；chat 这类 **开放生成、高熵** 任务上接受率明显下降。这一分层恰恰为置信度调度提供了用武之地——高熵查询更需要按存活概率裁剪验证长度，避免浪费批容量。

### 5.3 消融与分析（Figure 2–6）

**位置分析（Figure 2，逐位置接受率）**：揭示三种 drafter 的互补结构——
- **Position 1**：DFlash 接受率 **高于** Eagle3。得益于 5 层深层骨干，DFlash 在块首预测上更强；
- **尾部（suffix）**：Eagle3 接受率**稳定甚至上升**（自回归天然建模前缀依赖），而 **DFlash 随位置快速衰减**（suffix decay，块内 token 互不依赖）；
- **DSpark**：**继承两者之长**——块首借深层并行骨干拿高接受率，尾部借轻量顺序头（Markov/RNN）注入依赖，抑制衰减，整条曲线高于任何单一范式。

**深度实验（Figure 3）**：**2 层 DSpark > 5 层 DFlash**。半自回归的顺序依赖建模让浅得多的 DSpark 在接受长度上反超深层并行基线，证明性能瓶颈是 **块内依赖缺失** 而非容量不足——这为轻量化部署提供了直接依据。

**长度实验（Figure 4，draft 长度 $\gamma$）**：随 $\gamma$ 增大，DSpark 的相对优势 **单调扩大**（DFlash 因 suffix decay 在大 $\gamma$ 下崩塌，Eagle3 因 $T_{\text{draft}} \propto \gamma$ 难以承受大 $\gamma$）。更关键的是，DSpark 引入的顺序头 **延迟开销仅 0.2%–1.3%**（$\gamma$ 从 4 到 16）——轻量顺序头的额外计算几乎可忽略，$\tau$ 提升却显著，性价比极高。

**置信度头有效性（Figure 5–6）**：
- **Figure 5**（阈值扫描）：在 chat 域上，以置信度阈值过滤高风险 token，接受率从 **45.7% → 95.7%** 大幅跃升，证明置信度信号能可靠区分"高/低存活"前缀；
- **Figure 6**（STS 校准）：原始置信度头 **ECE 3%–8%**（存在过自信/欠自信），经 **STS（Stepwise Temperature Scaling）** 从左到右逐位置温度缩放后 **ECE ≈ 1%**。校准后的概率可直接喂给调度器做存活概率估计，保证 Algorithm 1 的 early-stopping 决策无偏。

### 5.4 生产部署（Figure 7–8）

DSpark 部署于 **DeepSeek-V4 serving system** 实际用户流量，对比既定生产基线 **MTP-1**（multi-token-prediction，单 token 验证）。两套硬件配置：

| 系统 | SLA | 吞吐提升（matched-latency） | 单用户加速（matched-throughput） |
|------|-----|----------------------------|--------------------------------|
| **V4-Flash** | 80 TPS | **+51%** | **+60%–85%** |
| **V4-Pro** | 35 TPS | **+52%** | **+57%–78%** |

**解读**：
1. **两套 SLA 下吞吐均提升约一半**（+51% / +52%）——置信度调度避免了对高拒答 token 的浪费验证，把批容量让给真正能被接受的请求；
2. **matched-throughput 下单用户速度提升 57%–85%**——相同系统吞吐下，每个用户感受到的生成速度近乎翻倍，直接改善交互体验；
3. **Pareto 前沿外推**：MTP-1 在严苛 SLA 下会因验证浪费而吞吐崩塌，DSpark 防止了这种崩塌，**解锁了此前不可达的性能档位**（shifts the Pareto frontier）。

**自适应行为（Figure 8，高并发）**：随着并发上升，调度器 **自动缩短验证长度**——从宽松负载下的 **4–6 tokens** 自动收紧到高负载下的 **2 tokens**。这是负载感知调度的直接体现：当批容量紧张时，宁可放弃部分接受长度也要保住全局吞吐，由 Algorithm 1 的逐请求排序 + early-stopping 在线决策，且全程保持 **lossless**（无损保证由 Appendix A 的 early-stopping 必要性证明支撑）。

## Ch7 局限与延伸

### 7.1 局限性

1. **固定 draft 开销**：半自回归的并行骨干 + 顺序头每个 verify step 都要 **先完整生成 $\gamma$ 个 draft token**，$T_{\text{draft}}$ 是固定的硬件成本。即便置信度调度裁掉了验证长度，draft 这一前向的开销 **已经发生**——无法在 draft 阶段就依据难度自适应缩短生成（不像自回归 drafter 可以动态停）。

2. **低接受率查询下的不可恢复计算**：当某个请求整体置信度极低（例如极端高熵的 chat/创意生成），整块 $\gamma$ 个 draft token 极可能全被拒。此时 draft 的算力与该次 verify 的批容量 **属于不可恢复的浪费**。置信度调度只能 *事后* 裁剪验证长度以保护其他请求，无法 *事前* 撤回已生成的 draft。

3. **领域依赖**：5.2 的 domain effect 表明，增益在 math/code 上最显著，而 chat 域 $\tau$ 仅 3.2–3.7，绝对值仍偏低。对开放生成的加速天花板受限于目标模型本身在该域的熵，drafter 改进空间收窄。

### 7.2 相关工作定位（推测解码算法谱系）

DSpark 处于推测解码方法演进的特定节点，谱系可概括为：

$$\text{standalone LM} \;\to\; \text{multi-token heads} \;\to\; \text{self-spec} \;\to\; \text{parallel drafters}$$

- **standalone LM**：用独立小模型做 drafter（经典 speculative decoding）；
- **multi-token heads**：在目标模型上加多 token 预测头（MTP），如生产基线 MTP-1；
- **self-spec**：复用目标模型自身的中间层做 draft（Eagle3 类）；
- **parallel drafters**：单前向并行生成整块（DFlash、DSpark 骨架所在）。

DSpark 的定位：在 **parallel drafters** 这一最新分支上，**首次同时解决 suffix decay（半自回归）与验证浪费（置信度调度）** 两个并行范式的固有缺陷，并在生产流量上验证。

**系统调度方向**的并列脉络为：**adaptive length → confidence-based → bandit**。DSpark 属其中的 confidence-based 一脉（用置信度头 + STS 校准估计存活概率），区别于纯自适应长度（按负载经验裁剪）与 bandit（在线试探最优 $\gamma$）。三者可视为调度信号从"盲调"到"有偏估计"到"在线学习"的演进。

### 7.3 未来方向

**Difficulty-aware early exiting**：针对 7.1 的"固定 draft 开销"与"不可恢复计算"，自然的下一步是把自适应从 **验证阶段** 推进到 **draft 阶段**——根据输入难度（如目标模型对前缀的熵估计）动态决定是否生成、生成多长，对低置信请求 **提前退出 draft**，从源头消除浪费。这与 DSpark 的置信度调度一脉相承，本质是把"按存活概率调度验证长度"升级为"按难度调度 draft 长度"，进一步把 Pareto 前沿向左下推。
